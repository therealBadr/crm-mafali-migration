# Mafali CRM — Risk Register v1

Populated so far from: Part 2 (data schema) and the Client Management module (Part 3). Will grow as remaining modules are reviewed.

| # | Risk | Probability | Impact | Mitigation | Priority |
|---|---|---|---|---|---|
| 1 | Client primary key (Cle_Opl) is generated by scanning for max+1 in application code, not a DB sequence — concurrent creation could collide | Low-Medium (depends on concurrent usage patterns, unconfirmed) | High (silent data corruption: two clients sharing one key) | Replace with real auto-increment/UUID in new schema; audit legacy data for existing collisions before migration | High |
| 2 | No formal foreign keys anywhere in the schema (0 declared relationships) — all joins are implicit, some with type mismatches (e.g. signed vs unsigned client ref) | Confirmed present | Medium-High (referential integrity unknown until data is inspected) | Run data-quality audit on production data before migration; add real FKs in new schema | High |
| 3 | Excel client import has no deduplication — re-running an import creates duplicate client records | Unconfirmed usage frequency | Medium | Confirm how often this is used; if kept, add upsert-by-key logic in new system | Medium |
| 4 | Hard delete on client records, no soft-delete flag, no audit trail of who/when | Confirmed present | High (permanent, unrecoverable data loss; no accountability) | Recommend explicitly changing this behavior in the new system (soft delete + audit log) even though it deviates from "faithful" replication — current behavior is a liability, not a considered business rule | High |
| 5 | Assistantes reference table has no unique key/auto-ID at all; the "commercial assistant" dropdown in the main workflow screen actually reads from a different table (GPWUtilisateur, part of the auth component), not Assistantes | Confirmed present | Medium (domain model confusion; possible dead data) | Confirm whether Assistantes.FIC is used anywhere before deciding whether to model it at all | Medium |
| 6 | CA (revenue) table's client+year uniqueness is only a non-unique index at the DB level — **however, confirmed the main entry screen (Fiche_CA) actively blocks duplicate client/year entries in application code**, so normal usage is protected. Only bulk-import or direct-edit paths could bypass it. | Confirmed present, lower severity than first assessed | Low-Medium (financial reporting accuracy, only via non-standard paths) | Add a real DB constraint in the new schema as defense in depth; check production data for pre-existing duplicates from historical import activity | Medium |
| 7 | Historique.FicStk and similar binary-memo fields store file attachments directly in the HFSQL database | Confirmed present | Low-Medium (affects DB size/backup strategy, not correctness) | Decide during architecture phase: keep BLOB-in-DB or move to object storage with a reference column | Low-Medium |
| 8 | Excel import path is hardcoded to a specific, likely non-existent legacy machine/user profile (`C:\Documents and Settings\fe\...`) | Confirmed present | Low (breaks import feature if still relied upon, but easy to notice) | Confirm current usage; replace with proper file-upload UI in new system regardless | Low |
| 9 | Help system is a compiled Windows CHM file, referenced from nearly every screen | Confirmed present | Low (not a data risk, but a real scope item) | Plan for a replacement in-app help system if contextual help is in scope for v1 of the new CRM | Low |
| 10 | `gsRechercherVille` (postal-code-to-city lookup) is an untraced external dependency | Unconfirmed source | Medium (unknown whether it's a local table, hardcoded list, or external service call) | Locate definition in Part 5 (procedure collections) or external components before finalizing integration architecture | Medium |
| 11 | Two client-editing screens exist (Fen_Detail_Client, simple; Fen_Parcours_Client, full-featured) with inconsistent behavior (e.g. postal-code autocomplete active in one, disabled in the other) | Confirmed present | Medium (risk of replicating a dead/legacy screen unnecessarily, or missing a still-used one) | Ask business stakeholders which screen(s) are actually used day-to-day | Medium |
| 12 | EtatClient appears to have both a coded (1/2) and text ("Client"/"Prospect") representation used inconsistently across screens | Confirmed present | Low-Medium (data-type ambiguity for migration mapping) | Inspect actual stored data values before finalizing field type in new schema | Medium |
| 13 | Historique (the interaction audit log) is fully editable and hard-deletable via Fen_Fichier_Historique / Fen_Detail_Historique — no field validation, no restriction on which fields can change (including re-pointing a row to a different client), no soft delete, no audit-of-the-audit | Confirmed present | High if Historique is relied on as a trustworthy record of what happened; Low if it's understood internally as just a working log | Decide explicitly: does the new system need Historique to be a tamper-evident audit trail? If yes, this is a deliberate architecture change (append-only + edit history), not a faithful replication | High |
| 14 | Three separate, inconsistent Excel import/update mechanisms exist (Fen_Fichier_Client's naive always-insert import, Fen_Update's proper upsert, and FEN_Modification_Depuis_Excel, not yet reviewed) | Confirmed present (2 of 3 reviewed) | Medium (scope/confusion risk — don't want to replicate all three) | Ask the business which one(s) are actually used | Medium |
| 15 | Fen_Choix_Mois_Rappel (month-offset reminder picker) appears to be dead code — its only caller is commented out | Likely | Low (irrelevant if truly unused) | Confirm with business before deciding to drop it from scope | Low |
| 16 | Four distinct UI paths exist for editing client data (detail form, main workflow screen, search-screen "apply modification," and in-place grid edit from the filter screen), with inconsistent field-level behavior between them (e.g. postal-code autocomplete active in one, disabled in another) | Confirmed present | Medium (scope and consistency risk for the new system) | Ask which paths are actually used day-to-day; consolidate in the new system unless there's a real reason for each to exist separately | Medium |
| 17 | Minor copy-paste text defects in confirmation dialogs (wrong entity name in "are you sure you want to delete" messages) | Confirmed present, cosmetic | Low | No action needed beyond awareness; worth a broader text-string audit given the pattern | Low |
| 18 | Four separate, overlapping Excel import/export mechanisms exist (naive insert, proper upsert, rich insert-with-autogenerated-ID, rich update-with-clear-sentinel), each generating client IDs or matching records differently | Confirmed present (all 4 reviewed) | Medium-High (scope, data-quality, and consolidation risk) | Ask the business which mechanism(s) are actually in current use; design one clean import feature for the new system informed by the best ideas from all four (the Cle_Opl-match upsert logic and the "#"-to-clear sentinel are worth keeping conceptually) | High |
| 19 | Two Excel import paths silently auto-create new Type_Franchise reference rows for unrecognized franchise names, bypassing the admin screen entirely | Confirmed present | Medium (reference-data integrity; "canonical" list isn't fully controlled) | Decide deliberately: keep auto-provisioning behavior or switch to validate-and-reject in the new system | Medium |
| 20 | A manual "Reindex Database" admin tool exists (rebuilds indexes, releases transaction locks) — its presence suggests the legacy HFSQL file-based database has had recurring index-corruption or lock-contention issues under real usage | Unconfirmed frequency of use | Low for the new system itself (a modern RDBMS handles this automatically) but signals possible current data-quality issues to check before migration | Ask staff how often this tool is actually run; if frequently, treat as a signal to scrutinize data integrity extra carefully during migration | Medium |
| 21 | **CRITICAL: user passwords are stored and compared in plaintext** (uppercased, no hashing/salting whatsoever) in the authentication component | Confirmed present | Critical — a full password-database compromise would expose every user's actual password in readable form | Non-negotiable for the new system: proper password hashing (bcrypt/argon2) from day one. Also means legacy passwords cannot be migrated as-is — users will need a forced password reset during cutover | **Critical** |
| 22 | Login lockout after 3 failed attempts only closes the login window — no persisted attempt counter or time-based lockout, so it provides negligible brute-force protection | Confirmed present | Medium (weak but not the top concern given #21) | Implement real rate-limiting / account lockout in the new system | Medium |
| 23 | The permission/auth component (GPW/WDGPU) supports per-window, per-UI-element granular permissions — a much finer grain than typical modern RBAC. Unknown whether this granularity is actually used in practice or everyone effectively has full access via the unrestricted default role | Unconfirmed | Medium-High (scope risk: replicating this fully would be a significant, likely unjustified, engineering investment) | Ask the business whether any staff currently have restricted/custom permissions; if not, build simple screen/feature-level RBAC instead | High (scoping decision) |
| 24 | Connection/login history can be entirely wiped by a supervisor with one confirmation — same "erasable audit trail" pattern as Historique (#13) and hard client deletion (#4) | Confirmed present | Low-Medium | Cover in the same deliberate architecture decision as #13: decide once whether any of the system's audit trails need to be tamper-evident, and apply consistently | Medium |
| 25 | The auth/permissions component (GPW/WDGPU) is confirmed to be a generic, mature, reusable AHG library (own internal migration tooling, multi-application user pool, LDAP import, drag-and-drop admin UI) — not Mafali-specific code | Confirmed | N/A — this is a scoping finding, not a defect | Replace with standard modern auth/RBAC rather than port; recommend against replicating this component 1:1 | High (architecture decision) |
| 26 | The startup "today's reminders" popup depends on a boolean flag (France_Optique.RappelRDV) that no reviewed workflow screen appears to actually set — the normal save flow only writes Date_Rappel/Heure_Rappel | Unconfirmed — may be a gap in my review, or a genuinely under-used/broken feature | Medium (if broken, staff may believe reminders work when the popup is actually empty or incomplete) | Ask staff directly: does the daily reminder popup show useful data today? If not, treat as confirmation the feature is effectively dormant | High (verify before designing the new reminder feature around this logic) |
| 27 | `gsRechercherVille` (postal-code-to-city autocomplete) is confirmed to be an external dependency not present anywhere in the 1602-page source documentation | Confirmed | Low-Medium (feature can't be ported without finding the original component) | Ask whether the original WinDev project's external components/DLLs are available separately; if not, this feature will need a modern equivalent (e.g. a French address/postal-code API) rather than a port | Medium |
| 28 | Zero automated test coverage exists in the legacy application (one trivial recorded test, explicitly noted as no real tests) | Confirmed | Medium (no executable spec or regression safety net to validate "faithful replication" against) | Plan for thorough manual UAT during migration; build the new system with real automated tests from the start | Medium |

## Summary

All 46 windows, all 8 queries, both procedure collections, the automated-test suite, and the internal WDGPU auth component have now been reviewed (WDGPU sampled rather than exhaustively read once it was confirmed to be a generic third-party-style library with no unique business logic — see the functional spec for justification). 28 risks logged: one Critical (#21, plaintext passwords), several High-priority scoping decisions (#13 audit-trail integrity, #18 Excel import consolidation, #23 permission granularity, #26 reminder-flag gap), and the rest Medium/Low data-quality and consistency items.

No hard blockers to the migration — everything found is a design decision to make deliberately, not a reason to stop. Risk #13 (editable/deletable audit trail) and #21 (plaintext passwords) are the two most worth raising directly with stakeholders before database and auth design are finalized.
